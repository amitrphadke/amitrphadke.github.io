MCQ tactics — how to earn marks you did not study for

You need roughly 37 of 53. Tactics reliably convert a chunk of your unknowns into marks.

  • Answer every question. There is no negative marking. An unanswered question is a guaranteed zero; a guess between two survivors is a coin flip.
  • Eliminate absolutes. Options containing always, never, only, all, must never are usually wrong. Real engineering answers are conditional. Options saying it depends on X, when Y, prefer Z are usually right.
  • The option that does more work for less privilege usually wins. Anthropic's documented guidance consistently favours: the simplest thing that works, least privilege, validate everything, keep a human on irreversible actions, prefer the cheapest model that passes your eval.
  • Two options that say the same thing in different words are both wrong. If A and C are paraphrases, the answer is B or D.
  • The longest, most qualified option is right more often than not — correct answers need caveats; wrong ones are crisp and clean.
  • Read the last line of the stem first on long scenarios. "Which is MOST cost-effective?" and "Which is MOST secure?" have different answers to the same scenario. Find the adjective before you read the story.
  • Scenario questions: find the constraint. High volume → cheaper tier. Latency-sensitive → no batching, consider streaming. Irreversible → human approval. Untrusted content → treat as data. Repeated identical prefix → caching.
  • If two options are both technically true, pick the one that answers the asked question, not the one that is most impressive.
  • Flag and move. 120 minutes for 53 questions is ~2m15s each. If you are 90 seconds in with no progress, mark your best guess, flag it, move on. Come back with the time you saved.
  • Later questions leak answers to earlier ones. Terminology in a question you can answer often disambiguates one you flagged.
Trap pattern: an option that is true in general but does not solve the scenario's stated problem. Example: "lower the temperature" is a true sentence about reducing variability, and the wrong answer to almost every question about length, cost or truncation.

Applications & Integration 33.1% ≈18 questions

Request anatomy

  • model (required). Dated id = pinned snapshot; alias moves to the newest. Pin dated ids in production.
  • max_tokens (required) caps output only. It is a hard stop, not a hint.
  • messages (required): list of {role, content}. Roles are only user and assistant, must alternate, first must be user. Content is a string or a list of blocks.
  • system is a top-level parameter, not a message role. Role, rules, stable reference material.
  • temperature 0–1. top_p/top_k are legacy; do not send both temperature and top_p; newest models reject non-default values.
  • stop_sequences, stream, tools, tool_choice, thinking, metadata.
Two consecutive same-role messages = 400. Merge them into one message with several content blocks.

stop_reason — the single most-tested field

end_turnFinished naturally. Normal.
max_tokensYou cut it off. Raise max_tokens or ask for less. Not a model failure.
stop_sequenceHit one of your stop strings; stop_sequence names which.
tool_useYour turn to act: run the tool, return results, call again.
refusalModel declined. A terminal state to handle, not an error to retry around.
pause_turnLong-running server tool paused; continue the turn.

The tool loop

  1. Call with tools. Response has stop_reason: "tool_use" and one or more tool_use blocks (each with id, name, input).
  2. Append the assistant message unchanged.
  3. Append one user message containing a tool_result block per tool_use, each with the matching tool_use_id.
  4. Call again. Repeat until end_turn.
  • Tool failed? Return tool_result with is_error: true and the message. The model recovers. Never leave a tool_use unanswered — that is a 400.
  • tool_choice: auto (decide) · any (must use one) · tool (must use this one) · none (must not). disable_parallel_tool_use forces one at a time.
  • Forcing a tool is the classic way to get structured extraction — schema in input_schema, read block.input.
  • Server tools (web search, web fetch, code execution) run on Anthropic's side: you see server_tool_use and a result block, you return nothing. Client tools you execute yourself. Cap server tools with max_uses.
  • The tool description is the interface. Vague or overlapping descriptions cause wrong tool choice.

Streaming

Event order: message_start → (content_block_start → content_block_delta* → content_block_stop)* → message_delta → message_stop. Plus periodic ping.

Where usage livesInput tokens in message_start. Final stop_reason and cumulative output_tokens in message_delta. Streaming changes delivery and time-to-first-token, never cost.

Structured output

Reliability, weakest to strongest: plain instruction < prefill (legacy) < forced tool < structured outputs. Always parse, validate against a schema, and retry once with the validation error appended. Treat model output as untrusted input.

Prefill is incompatible with extended thinking.

Vision and documents

  • Image block: {"type":"image","source":{"type":"base64"|"url", ...}}. Document block for PDFs: {"type":"document", ...}.
  • They go in a user message, as blocks, before the question.
  • PDFs are charged as text plus an image per page, and have page and size ceilings. Oversized → 413.
  • citations: {enabled: true} is opt-in per document; answers come back with source spans attached.

Prompt caching

  • Mark the end of the stable prefix with cache_control: {"type":"ephemeral"}. Everything before the breakpoint is cached. Up to 4 breakpoints.
  • Prefix order is fixed: tools → system → messages. Change something early and every cache after it is invalidated.
  • Minimum cacheable length (~1024 tokens on Sonnet/Opus, higher on Haiku tiers). Below it, the breakpoint is silently ignored — the single most-tested caching trap.
  • Default TTL 5 minutes, refreshed on each hit; a longer 1-hour option exists at a higher write price.
  • Writes cost more than normal input; reads cost a fraction. One write needs several reads to pay off — so cache for reuse, not for size.
  • Check usage.cache_read_input_tokens > 0 to prove a hit. cache_creation_input_tokens is the write.

Message Batches

  • 50% cheaper, results within 24 hours (usually far sooner). Up to ~100k requests / 256MB per batch; results retrievable for 29 days.
  • Match results to requests by custom_id — results are not in submission order.
  • Four result types: succeeded, errored, canceled, expired.
  • Use when nobody is waiting. Never for interactive work; incompatible with streaming.

Errors

400invalid_request — your bug (bad roles, unanswered tool_use, bad schema)
401 / 403auth / permission — the key
404not found
413request too large — split the document
429rate limit — honour retry-after, then back off
500Anthropic's fault — retry
529overloaded — retry

Retry 429 / 500 / 529 with exponential backoff and jitter. Everything else is a fix, not a retry. SDKs retry a couple of times by default (max_retries). Rate limits are RPM, input TPM and output TPM; anthropic-ratelimit-* headers report what is left.

Statelessness

The API stores nothing. You resend the whole transcript each turn, so input tokens grow every turn — the reason long chats need summarisation or caching, and the reason agent loops get expensive.

count_tokens is a free pre-flight input count (supports tools, system, images, PDFs). It does not predict output.

Model Selection & Optimisation 16.8% ≈9 questions

Picking a tier

HaikuFastest, cheapest. Classification, extraction, routing, moderation, high volume.
SonnetThe default workhorse. Most production work, balanced cost and capability.
OpusHardest reasoning, agentic coding, long-horizon planning. Reach for it last.
The rulePick the cheapest tier that passes your eval. And cost optimisation is a function of volume: at 50 calls a day, buy the quality; at 2 million, buy the savings.

Cost levers, in order of impact

1. Model choice (changes the per-token rate) → 2. Caching (repeated prefix to a fraction) → 3. Prompt length (incremental) → 4. Batching (flat 50% on what is left).

Measure cost per successful task, not per token: a cheap model that needs retries or human escalation can cost more overall.

Extended thinking

  • Manual: thinking: {type:"enabled", budget_tokens: N} where N ≥ 1024 and N < max_tokens.
  • Newer models: {type:"adaptive"} with an effort setting — the model scales its own reasoning. Prefer it where available.
  • Thinking tokens are billed as output.
  • Incompatible with: forced tool_choice, prefill, and changing temperature/top_p.
  • Worth it: multi-step maths, planning, hard debugging. Waste: lookup, extraction, classification, formatting.

Context window

Window = input + output in one request. max_tokens caps only the output half. Overflow raises model_context_window_exceeded — distinct from max_tokens truncation, which is self-inflicted.

Near the limit: cache the stable, retrieve only the relevant, summarise the old, keep recent turns verbatim. Quality degrades before it errors.

Platforms

Claude API, Amazon Bedrock and Google Vertex serve the same models. Choose on data residency, compliance boundary, existing cloud contracts and ops — not capability.

Agents & Workflows 14.7% ≈8 questions

The defining distinctionWorkflow = predefined code paths you wrote. Agent = the model decides the path at runtime. Prefer the simplest thing that works; most production "agents" should be workflows.

The five patterns

Prompt chainingSequential steps, with gates in code between them. Trades latency for accuracy.
RoutingCheap classifier picks one specialist branch. The classic cost-and-quality win.
ParallelisationSectioning: different subtasks at once. Voting: same task n times, take the majority — buys confidence with tokens.
Orchestrator-workersA model decides the subtasks at runtime and delegates. (Versus parallelisation, where you fixed them in advance.)
Evaluator-optimiserGenerate → critique → revise, looping to a stated quality bar.

The agent loop and its guards

model → tool call → observe result → repeat → stop. Named failure modes: infinite loops, runaway cost, hallucinated tools, lost context, unapproved destructive actions.

  • Always: a max-turn cap and a cost ceiling.
  • Loop detection: same tool + same arguments N times in a row → break out and tell the model.
  • Irreversible actions need human approval enforced in code, never by instruction.
  • Observe before acting — a cheap read beats a wrong write.

Subagents

Exist for context isolation: the noisy search happens in their window, the parent receives only the conclusion. Give them restricted tools. You must pass them everything they need, because they cannot see the parent's context.

Agent SDK

Claude Code's loop as a library: built-in tools, the tool loop, permission prompts, context compaction, CLAUDE.md loading, MCP, subagents, hooks. Use the raw Messages API when you need full control or a non-filesystem agent.

Prompt & Context Engineering 11.0% ≈6 questions

Technique order (memorise the sequence)

1. Be clear and direct → 2. Multishot examples → 3. Let it think (chain of thought) → 4. XML tags → 5. System prompt role → 6. Prefill → 7. Chain prompts → 8. Long-context tips.

  • Long documents go first, the question last. One of the best-measured long-context behaviours.
  • XML tags separate instructions from data — a quality technique and the first line of injection defence.
  • Examples beat adjectives. Three or four covering the edge cases beat any amount of describing. Too many examples crowd the window and bias output.
  • Specific and checkable beats polite and vague. "Exactly three bullets, under 20 words each, covering risk, cost, timeline" — not "summarise well".
  • What goes where: system = role, rules, stable reference (and your cache prefix). user = this call's task and data. assistant = prefill only.

RAG, briefly

  • Retrieve when the corpus exceeds the window or when most of it is noise for this question.
  • Chunking: too small loses context, too large retrieves noise; overlap protects boundaries.
  • Hybrid search: embeddings catch meaning, BM25 catches exact tokens (error codes, identifiers). Rerank the merged list.

Tools & MCP 10.6% ≈6 questions

Who controls what — guaranteed to be testedTools = model-controlled. Resources = application-controlled. Prompts = user-controlled.
  • MCP is JSON-RPC 2.0. Handshake: initialize → capability negotiation → then tools/list, tools/call, resources/read, prompts/get.
  • Architecture: host → client → server.
  • Transports: stdio = local child process. Streamable HTTP = remote. A remote server cannot use stdio; a hosted API cannot spawn a stdio server.
  • Sampling: the server asks the host's model for a completion, mediated by the client — model access stays with the host.
  • Roots: the client tells the server which directories/URIs it may touch — a least-privilege boundary.
  • Also: log and progress notifications.
  • The Messages API's MCP connector reaches remote HTTP servers and surfaces their tools as mcp_tool_use / mcp_tool_result; restrict with allowed_tools.
  • Plain tool vs MCP server: one app needing one function → a tool. Several hosts, discoverable, reusable, remote → an MCP server.
  • Skills vs tools vs MCP: a tool is one function; a Skill packages instructions and files for a task; MCP is the protocol serving tools, resources and prompts.

Security & Safety 8.1% ≈4 questions

  • Indirect prompt injection is the threat — hostile instructions arriving inside documents, tool results, web pages, issue comments. Not the user typing an attack.
  • Defences, in order of actual effectiveness: least-privilege tools → human approval on irreversible actions → separate data from instructions with XML tags and state it is untrusted → validate inputs and outputs → monitor and log.
  • Instructions reduce likelihood; privilege limits bound the damage. If an option says "tell the model to ignore instructions in documents" as the whole answer, it is the weaker choice.
  • Never a general shell or full-database tool. Narrow verbs, validated arguments, allow-listed targets. A JSON schema checks shape, not authorisation.
  • PII: minimise what you send, redact what the task does not need, and keep it out of logs — logs usually have a wider audience than the system.
  • A cheap moderation model in front of the expensive one is both a safety and a cost control.
  • stop_reason: "refusal" is a normal terminal state to handle gracefully.

Claude Code 3.1% ≈2 questions

  • CLAUDE.md = project memory, committed at the repo root, loaded into every session. Keep it short. @path imports.
  • Precedence, highest first: managed policy → user (~/.claude/) → project (committed) → local (git-ignored).
  • Commands (.claude/commands) are user-invoked via /name, with $ARGUMENTS. Skills are model-invoked from their description. Hooks are deterministic shell on lifecycle events. Subagents (.claude/agents) get their own context and tool set. MCP brings external tools. Plugins bundle these.
  • Hook exit codes: 0 = allow, 2 = block (stderr is returned to Claude), other = non-blocking error.
  • Permission modes: default (ask) · acceptEdits · plan (read-only) · bypassPermissions (sandboxes and CI only).
  • Headless: claude -p with --output-format json, --allowedTools, --max-turns for CI.

Eval, Testing & Debugging 2.6% ≈1–2 questions

  • Workflow: build a test dataset → run the prompt over it → grade → track the score over time. The tracking is what catches regressions when a prompt or model changes.
  • Code-graded whenever the answer is checkable exactly (value, schema, number) — faster, cheaper, deterministic. Model-graded only for open-ended qualities, and then with a clear rubric and spot-checks of the judge against human labels.
  • Debug order: stop_reason → usage → the message list → response headers. Most "the model is broken" reports are truncation, a missing tool_result, or role order.

The last five minutes — read twice

  1. max_tokens caps output. stop_reason: max_tokens means you truncated it.
  2. system is top-level. Message roles are user and assistant only, alternating, user first.
  3. N tool_use blocks → one user message with N tool_result blocks, matched by tool_use_id. Failure → is_error: true.
  4. Final stop_reason and output tokens arrive in message_delta.
  5. Caching: order is tools → system → messages; under the minimum length the breakpoint is silently ignored; writes cost more, reads cost a fraction; cache for reuse, not size.
  6. Batches: 50% off, within 24h, match by custom_id, four result types, never interactive.
  7. Retry 429 / 500 / 529 and honour retry-after. Everything else is your bug.
  8. The API is stateless — input tokens grow every turn.
  9. Cheapest tier that passes the eval. Cost levers: model → cache → prompt → batch.
  10. Thinking: ≥1024 and < max_tokens, billed as output, no forced tool_choice, no prefill. Useless on lookups.
  11. Workflow = fixed path. Agent = model decides. Orchestrator-workers decides subtasks at runtime.
  12. Every agent needs a turn cap and a cost cap; irreversible actions need a human gate in code.
  13. Subagents = context isolation.
  14. MCP: JSON-RPC 2.0, initialize first. Tools = model, resources = app, prompts = user. stdio local, Streamable HTTP remote.
  15. Injection arrives in data. Least privilege and human approval bound the damage; wrapping in XML tags reduces the odds.
  16. Prompting order: clear and direct → examples → let it think → XML → system role. Documents first, question last.
  17. Hook exit 2 blocks. Permission modes: default, acceptEdits, plan, bypassPermissions.
  18. Evals: dataset → run → grade → track. Code-grade what you can check exactly.
  19. Debug: stop_reason → usage → messages → headers.
  20. Answer every question. Eliminate absolutes. Find the adjective in the stem. Flag and move at 90 seconds.
